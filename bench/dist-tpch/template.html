Where distributed Sirius spends q5's three seconds

Four Sirius processes, one per GPU, each scan a quarter of the files and exchange batches over NIXL. With the data held in Sirius's pinned host cache, q5 runs in {{WARM_EXEC}} s. The lineitem scan, with its runtime filter and its shuffle on the order key, takes {{LI_SHARE}}% of that. The first run takes 109 s because it reads the data from one local NVMe drive.

The run

The same build ran the same query text three ways. Each run is one process per rank running the query three times: the first is cold, the best of the other two is warm.

The query

SELECT n_name, sum(l_extendedprice * (1 - l_discount)) AS revenue
FROM orders, lineitem, supplier, nation, region, customer
WHERE c_custkey = o_custkey AND l_orderkey = o_orderkey
  AND l_suppkey = s_suppkey AND c_nationkey = s_nationkey
  AND s_nationkey = n_nationkey AND n_regionkey = r_regionkey
  AND r_name = 'EUROPE'
  AND o_orderdate >= date '1997-01-01' AND o_orderdate < date '1998-01-01'
GROUP BY n_name
ORDER BY revenue DESC;

At SF10000, lineitem has 60 billion rows and orders 15 billion. One year of orders is about a seventh of them, and EUROPE is one region in five.

General view

Every rank runs the same 47 pipelines on its own share of the files. The plan moves data between ranks in three ways, and DuckDB's join order puts lineitem last.

BroadcastA build side under 1 GiB goes to every rank, and the probe side stays where it was read: region, nation ⋈ region, and supplier.
Hash shuffleLarger joins hash both sides on the join key across the 4 ranks: customer and orders on the customer key, then the orders result and lineitem on the order key.
GatherPartial groups shuffle on n_name, a range exchange sorts them, and rank 0 collects the 5 rows.

Small tables · 0 to 0.12 s

Supplier, region and the nation ⋈ region result are broadcast. Customer is read where it lies and filtered by the nation keys before it joins.

{{STAGE_DIMS}}

Orders · 0.12 to 0.70 s ({{ORD_SHARE}}% of the query)

Each rank reads its quarter of orders in 13 tasks, keeps 1997 and the customer keys J2 produced, and shuffles the rest on the customer key for J3.

{{STAGE_ORDERS}}

Lineitem · 0.70 to 2.77 s ({{LI_SHARE}}% of the query)

Each rank reads its quarter of lineitem, about 15 billion rows, in 88 tasks from the pinned cache. A Bloom filter built from J3's order keys drops most rows on the GPU, and the rest is shuffled on the order key. Each rank's exchange source takes in 352 batches.

{{STAGE_LI}}

Joins, aggregate and result · 2.77 to 3.05 s

J4 and J5 run partition by partition (3 per rank), then a partial GROUP BY. The groups shuffle on n_name, are merged, sorted by a range exchange, and gathered on rank 0.

Warm iteration, per rank

{{WARM_TABLE}}
  • The ranks stay together. Each stage starts within 0.08 s across ranks, and the four finish within 0.01 s. The byte-range split gives each rank the same amount of work.
  • The lineitem scan runs about 4 tasks at a time. Its 88 tasks add up to 7.8 to 8.2 s of task time per rank, inside about 2 s.
  • The cache serves almost everything. In each warm iteration a rank reads about 128,550 chunks from the cache and misses 0 or 1. The cache evicts nothing.

Cold iteration, per rank

{{COLD_TABLE}}
  • The drive sets the cold time. Orders (90 GB) takes 16 to 18 s and lineitem (448 GB) 84 to 89 s, about 5 GB/s for the four ranks together. Once the last lineitem batch arrives, the joins and the result take about 0.1 s.
  • The first rank to finish waits. Lineitem scans end between 104.0 and 108.8 s, and J4 needs every rank's batches, so the rank that finishes first waits about 5 s.
  • Each rank caches about 128,450 chunks. That is its quarter of the 502 GB copy, and it fits in the 200 GiB host pool without evictions.

What to look at next

  • Lineitem's shuffle. Every rank sends three quarters of its filtered lineitem to the other ranks so J4 can join on the order key. Broadcasting J3's result instead would keep lineitem local. Whether that is cheaper depends on the size of J3's output, which these runs did not record.
  • Scan concurrency. About 4 lineitem tasks ran at once on each GPU. A run with more pipeline threads would show whether the scan is limited by threads or by the GPU.
  • Cold reads. Cold runs read from one NVMe drive at about 5 GB/s. GPFS reached 34 to 36 GB/s on this build. Filling the pinned cache from GPFS instead is the next thing to measure.
