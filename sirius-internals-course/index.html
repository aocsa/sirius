The mic hands back silently

Untranslatable idiom? The CPU takes over — correct results, and nobody hears the switch.

Concretely: Sirius is a GPU-native SQL engine shipped as a DuckDB extension. Compute runs on cuDF and RMM, with memory and data-movement primitives from NVIDIA cuCascade.

🧠
The whole engine in one sentence

Sirius intercepts a SQL query, converts DuckDB's plan into its own physical operators, expands them into pipelines, and turns eligible operator input into GPU tasks. Inside a task, returned operator_data moves forward from operator to operator; across pipeline boundaries, sinks publish data_batch references through repository-backed ports.

Method names do not classify an engine

DuckDB calling GetData(), Sirius returning operator_data, or a task popping a repository is only one boundary. Neither engine uses an end-to-end root next() recursion through the whole operator tree.

The swap happens in exactly one place

Sirius hooks DuckDB through an optimizer extension. The hook itself decides nothing about GPU support — it just captures the plan for a later verdict.

1
The hook copies the optimized logical plan

DuckDB's optimizer finishes; Sirius copies the plan into the connection's interception state. The shared engine context and active-query slot are separate lifetimes covered in Module 2. No GPU judgment yet.

2
OnFinalizePrepare runs create_plan()

sirius_physical_plan_generator::create_plan() walks the copy, building Sirius physical operators — or throwing at the first unsupported one.

3
Success wraps the plan; a throw falls back

Success: the plan is wrapped in PhysicalSiriusExecution and swapped in. Throw: DuckDB's own CPU plan runs, silently.

Plain English

The comment states the contract: create_plan() on this copy is the single source of truth for GPU support — no other code path gets a vote.

And the failure mode is spelled out up front: an unsupported operator means a throw, and the throw is the fallback signal.

Copy the plan so Sirius owns its own version — DuckDB keeps the original, untouched, ready for CPU execution.

Stash the copy in the connection's interception state; OnFinalizePrepare will pick it up once preparation finalizes.

Some plans can't even be copied (not serializable). No drama: quietly skip GPU — the user's query still runs on CPU.

Anything else unexpected gets logged at debug level. The user never sees an error, just a CPU-executed query.

Either way the query proceeds. GPU is an optimization, never a requirement.

💡
Key insight: GPU support is a plan-level decision, made once

create_plan() either succeeds (plan wrapped and swapped) or throws (silent CPU fallback). So when a query unexpectedly runs on CPU — or you wonder "will my new operator ever be used?" — there is exactly one gate to check.

One room, seven consoles

Think mission control: the Flight Director owns the go/no-go, the trajectory team plans the next burn, each spacecraft has its own ops crew, and life support quietly keeps everyone breathing. In Sirius the room itself is SiriusContext. The extension registers the same shared object with its connections; it is not a private engine per connection. 💡
Roles are strictly separated

Deciding what runs next (task_creator) is a different object — and different threads — from running it (the executors) and from surviving memory pressure (the downgrade executors). "Where do I put this logic?" and "whose thread am I on?" are the two questions that prevent broken PRs.

Reachability is not ownership

An operator may reach query state through its pipeline or context without owning that state. A shared_ptr<data_batch> keeps the batch object alive; it does not by itself mean the batch is locked, GPU-resident, or invisible to downgrade.

Push versus pull: classify the call path, not the method name

Jaffray's framing asks who controls the next transfer. In a pull iterator, a consumer recursively calls its child for another tuple or batch. In a push pipeline, a producer or pipeline driver hands an available batch to downstream operators.

The real reservation and feedback loop

1

Attempt admission

3
Relieve a shortfall

A partial result triggers one request_downgrade(predicate). After each conversion the predicate tries make_reservation_or_null(bytes_needs) and stops as soon as admission succeeds.

4
Run inside the budget

The task attaches its reservation-aware allocator to the CUDA stream, colocates input representations onto the reservation device, and executes operators.

5
Record failure evidence

On OOM, the task removes input-materialization bytes from the observed peak and calls record_on_failure(input_basis, peak_bytes) before rescheduling with its resume index.

6
Improve later in-query admission

Subsequent tasks or retries in that query call estimate_peak_memory(input_basis). Similar input bases receive more weight, and repeated failures retain the higher peak.

Multi-GPU: your room number comes from your booking

Since #732, tasks are dispatched by data locality — round-robin only when nothing has a preference. Which device your code runs on is decided by one thing: the device contract (SCHED-RR).

1
The reservation names the device

gpu_pipeline_task::execute takes its memory space from its reservation — the booking is the sole authority.

2
prepare_for_processing colocates everything

Every input batch is moved onto that memory space — before any operator runs.

3
Only then do operators run

An operator never asks a batch where it lives. Batches are guests; the booking decided the room.

⚠️
War story: push, pile-up, pin

#732’s greedy push scheduling piled tasks into per-GPU queues — beyond the downgrade executor’s reach, so their batches could never be spilled. #827 restored pull-signal backpressure: workers ask for work, queues stay shallow, victims stay reachable. And after cross-device SIGABRTs, #996 turned “prefer this device” into “pin this device” for cuco-backed operators.

FLOW

Push-oriented hybrid execution

Context: GPU tasks need forward batch execution, but pipelines must be independently admitted and memory-managed.
Decision: drive operator_data forward inside a task; buffer pipeline edges in repositories; discover readiness with hints.
Benefit: batching, asynchronous scheduling, barriers, and downgrade.
Cost: explicit completion/re-arm protocol and harder liveness reasoning.
Status/evidence: Current—gpu_pipeline_task, task_creator, operator sink/ports.
Revisit if: a unified driver can preserve those properties with measurably simpler lifecycle semantics.

AST

Translate once into sirius::ast

Context: DuckDB expression classes couple operator execution to one frontend.
Decision: translate at planning into native expression/value/function types; lower to cuDF AST or materialized operations later.
Benefit: a stable engine boundary and non-DuckDB frontend path.
Cost: Sirius owns translation, type coverage, AST breakers, and fallback tests.
Status/evidence: Current—src/expression/ and src/expression_executor/.
Revisit if: a frontend-neutral shared IR satisfies the same ownership and GPU-lowering requirements.

SPLIT

Expand compound operators into pipelines

Context: join, aggregate, and global sort need partition/build/merge phases with different barriers.
Decision: let sirius_pipeline_converter insert PARTITION/CONCAT and sample/partition/merge chains.
Benefit: explicit scheduling, device affinity, and phase-specific memory state.
Cost: more pipelines, wiring, IDs, and completion edges.
Status/evidence: Current—converter split helpers and plan printer.
Revisit if: an operator can expose equivalent phases without hiding scheduler-visible state.

WIRE

Describe wiring before materializing it

Context: pipeline conversion should not require live repositories or a runtime manager.
Decision: emit repository_wiring data, then materialize repositories, ports, consumers, and dependencies in initialize_internal().
Benefit: deterministic, testable planning and explicit runtime ownership.
Cost: two representations that must remain consistent.
Status/evidence: Current—compute_repository_wiring() and repository_wiring_materializer.cpp.

LOCK

Atomic state claim and task accounting

Context: completion can race a port pop or partition claim before the new task is counted.
Decision: hold the pipeline status lock across state consumption and the constructor that calls mark_task_created(); use RAII completion accounting.
Benefit: no empty-port/balanced-counter false finish.
Cost: a wider critical section and strict custom-task discipline.
Status/evidence: Current—load-bearing comment in sirius_pipeline.hpp.

Context: latency can be input wait, queueing, reservation, downgrade, GPU compute, or finalization; one timer cannot disambiguate them.

The channel contract

PROPOSED: this bounded, close-then-drain channel is a design target. No source file in the current tree provides this API.

Both operators stand on one primitive. Its contract fits on a card — read it as the spec your unit tests will assert:

Planned API — from the design notes, not yet in tree

exchange_channel — bounded, close-then-drain

{batch_id, size_bytes} What travels: a handle, never a batch. The batch is registered in a repository FIRST, then the handle is pushed.
try_push(h) False when full or closed; never blocks. The engine side only ever uses the try_ pair.
try_pop() Nullopt when empty; never blocks. Blocking push/pop exist only for the wrapper/test side.
close() Idempotent. Forbids new pushes — but queued items stay poppable: close-then-drain, not abort.
drained() closed() && empty() — the one true EOS predicate, same shape as split_connector::is_closed().

Why IDs? Module 6 separates ownership, lock state, residency, and discoverability. The proposal keeps the repository as the authoritative lookup so a queued item remains visible to current downgrade discovery:

1
Producer registers the batch in a repository

Ownership lands where the downgrade executor can see it — idle, unlocked, spillable.

2
Then it pushes {batch_id, size_bytes}

Two POD fields cross the channel. The channel holds metadata, never memory.

3
Your source resolves the id at task-creation time

pop_data_batch_by_id(h.batch_id) claims the batch from the repo only when a task is actually being built.

⚖️
The channel must never own memory

A shared_ptr<data_batch> would keep the object alive but would not itself lock it. The problem is a private channel becoming an unregistered owner outside repository and inspectable-queue discovery. The proposed ID preserves one authoritative repository lookup until a task claims the batch.

Install your own switch

A scan gets its completion evaluation for free — there’s always a task in flight to trip the sensor. A stream must install its own switch: every zero-task EOS path has to trigger the status evaluation itself. Any operator whose input isn’t the scan manager will face this exact gap.
