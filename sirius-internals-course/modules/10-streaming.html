The channel contract

DRAFT PR: this API is implemented in src/include/exec/exchange_channel.hpp in PR #1094 ↗, but it is absent from the pinned course tree, unmerged, and has no production wiring there.

Both boundary designs stand on one primitive. Its contract fits on a card — read it as the spec the PR’s unit tests assert:

Implemented core — draft PR only

exchange_channel — bounded, close-then-drain

{batch_id, size_bytes} What travels: a handle, never a batch. The batch is registered in a repository FIRST, then the handle is pushed.
try_push(h) False when full or closed; never blocks. The engine side only ever uses the try_ pair.
try_pop() Nullopt when empty; never blocks. Blocking push/pop exist only for the wrapper/test side.
close() Idempotent. Forbids new pushes — but queued items stay poppable: close-then-drain, not abort.
drained() closed() && empty() — the one true EOS predicate, same shape as split_connector::is_closed().

Why IDs? Module 6 separates ownership, lock state, residency, and discoverability. The implementation keeps the repository as the authoritative lookup so a queued item remains visible to current downgrade discovery:

1
Producer registers the batch in a repository

Ownership lands where the downgrade executor can see it — idle, unlocked, spillable.

2
Then it pushes {batch_id, size_bytes}

Two POD fields cross the channel. The channel holds metadata, never memory.

3
Your source resolves the id at task-creation time

pop_data_batch_by_id(h.batch_id) claims the batch from the repo only when a task is actually being built.

⚖️
The channel must never own memory

A shared_ptr<data_batch> would keep the object alive but would not itself lock it. The problem is a private channel becoming an unregistered owner outside repository and inspectable-queue discovery. The handle preserves one authoritative repository lookup until a task claims the batch.

Two verified defects still present in PR #1094

CONFIRMED AT 07d3ae71: these are not hypothetical review questions. The current channel and baseline task-creator control flow contain both gaps; the proposed fixes are not part of the two committed PR changes.

B1

Byte admission checks the past, not the candidate

try_push(h) asks full_unlocked() before adding h, but that helper sees only current _total_bytes. With a 50-byte limit and 40 bytes queued, a second 40-byte handle is accepted and the queue reaches 80. A 200-byte handle is also accepted into any non-full queue, not only an empty one.

B2

Terminal EOS can become true without an engine edge

close() notifies condition-variable waiters but fires no scheduling callback. If a hint resolves to null, manager_loop() continues before dispatching its lambda; the lambda’s final update_pipeline_status(false) therefore never runs. Empty streams and late close can hang forever.
