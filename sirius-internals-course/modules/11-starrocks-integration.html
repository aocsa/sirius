One system, three owners

The architecture works because the ownership lines are intentionally boring. StarRocks remains the distributed system; Sirius remains a single-fragment engine.

FE

StarRocks frontend

Owns SQL parsing, catalog and metadata, optimization, query coordination, fragment creation, and partition→CN assignment. It sends each CN an already-routed fragment; Sirius does not renegotiate that plan.

CN

Rust compute-node wrapper

Speaks StarRocks protocols upward, translates Thrift into Substrait, owns process and FFI lifetimes, and—in the target design—routes exchange data by stream id. It moves data; it does not implement GPU relational operators.

GPU

Sirius engine

Owns one fragment’s physical plan, pipelines, tasks, cuDF operators, cuCascade batches/repositories, reservations, and spill. It deliberately has no cluster topology or peer-CN awareness.

RULE
This is not distributed Sirius and not a Theseus rebuild

A bespoke cross-worker algorithm inside Sirius would duplicate or contradict the FE plan. Distributed-systems work belongs at the wrapper/session seam: exchange, sender-count EOS, backpressure, cancellation, and a safe shared GPU-memory budget.

The Rust binary is an adapter around an in-process engine, not a remote proxy to a separate Sirius daemon.

WIRE
BRPC compatibility does not mean a C++ BRPC runtime

The wrapper implements the Baidu PRPC frame and generates a Tower service facade from StarRocks protobuf definitions. The transport and frame parser are protocol adapters, not query execution.

The translation path preserves the FE’s decision

StarRocks has already optimized and fragmented the query. Translation changes representation; it must not quietly change distribution, partition routing, or expression meaning.

1
TExecPlanFragmentParams

The FE places a binary-Thrift plan, descriptor table, query options, fragment-instance id, sinks, and scan ranges in the BRPC attachment.

2
PlanTranslator::translate_fragment()

The Rust translator reconstructs flat preorder plan/expression lists using num_children, resolves slots through the descriptor table, and rejects under-run, trailing, or unsupported nodes explicitly.

3
Substrait Plan

Relations, expressions, output names, and extension-function anchors become a portable protobuf. to_substrait_bytes() is the intended FFI payload.

4
DuckDB logical plan → Sirius physical plan

Target handoff: Sirius uses its existing Substrait/DuckDB planning boundary, then lowers supported work into GPU operators and pipelines. DuckDB is an internal planning adapter here, not the cluster coordinator.

5
Per-fragment execution

Existing scheduler, reservations, cuDF operators, repositories, and downgrade machinery run the fragment. Output returns through a result sink or a streaming exchange sink depending on fragment position.

DON’T
Do not put a second optimizer in the translator

The translator may normalize representation and register Substrait extensions. It must preserve the FE’s fragment shape and routing. If a plan feature is unsupported, add an explicit mapping and parity test or reject it—never silently invent a different distributed plan.

What the pinned CN actually does today

Use this sequence when debugging the checked-out course snapshot. It is deliberately narrower than the target architecture.

1
Fail-fast engine bring-up

Args::run() constructs the real sirius::SiriusContext before opening RPC service. The handle is process-lifetime RAII.

2
Start services and register

The CN opens heartbeat, backend-Thrift, and BRPC listeners, then sends ALTER SYSTEM ADD COMPUTE NODE over the FE’s MySQL surface. Heartbeats establish identity; periodic reports keep the storage-less CN healthy.

3
Dispatch and translate

exec_plan_fragment validates the attachment protocol, deserializes TExecPlanFragmentParams, and calls the reusable translator. Batch dispatch merges common and per-instance parameters first.

4
Stub execution—the critical limit

Only a supported root RESULT_SINK is “executed,” and StubExecutor returns one string row per output column. Non-result sinks are translate-only. The separately created Sirius context is not passed into this executor yet.

5
Encode, buffer, fetch

The CN converts Arrow batches to StarRocks MySQL text rows, stores them by fragment-instance id, and serves one or more fetch_data polls with packet sequence and EOS. An unknown id is an error, not an empty result.

6
Ordered teardown

Shutdown stops RPC servers and background tasks before dropping the engine context, so no in-flight request can reach an already-destroyed GPU engine.

MEM
One GPU means one physical budget, even when software has two owners

The wrapper’s receive/staging buffers and Sirius compute allocations contend for the same device. The #840 design direction is a shared cuCascade reservation authority with exchange batches registered in repositories so downgrade can see them. It also needs receive-staging, copy-out, and send-copy credits to prevent “free memory by sending, but sending needs memory” deadlocks.

#840 budget modelBenefitCost / limitation
A. Shared cuCascade manager
design recommendation		One budget; registered exchange and compute batches can enter the same downgrade flow.Wrapper depends on cuCascade; borrow/lifetime, concurrent-query reentrancy, staging leases, and cross-stream synchronization need explicit contracts.
B. Partitioned budgetSimple isolation between wrapper and engine.Neither side can borrow capacity or spill the other side’s data; one partition can OOM while the other has free memory.
C. Wrapper-provided RMM allocatorKeeps the wrapper cuCascade-free.Sirius cannot see wrapper buffers as spill candidates and loses unified reservation semantics.
V1
Keep the first exchange queue inside Sirius

The pairing/sync direction is to let registered Sirius repositories and the existing downgrade executor handle pressure, accepting temporary cuCascade-type leakage into the wrapper. A pluggable downgrade interface for externally owned repositories is a future extraction, not a v1 dependency. Likewise, exposing live resource information through the stream session for receive-side tier placement is useful future policy, not permission to create a StarRocks-specific context.

For operator-level races, byte admission, terminal EOS, callback lifetime, and test gaps, return to Module 10. This module’s rule is simpler: the wrapper owns transport and stream routing; Sirius owns task admission and repository-visible memory.

Cross-CN transfer is a metadata-and-lease protocol

PROPOSED, ADAPTED FROM DORIS PRIOR ART: nixl moves registered buffers; the Rust wrapper owns every transport step. The engine sees only repository batches and channel handles.

1
Initialize one agent per CN

At startup the wrapper registers its staging arena and computes local agent metadata. The first transfer to a peer exchanges and caches agent metadata; a peer restart invalidates that cache.

2
Exchange per-batch metadata

The sender announces the batch layout and sizes over the side channel. The receiver leases addresses from a pre-registered GPU staging arena, or a host arena when the deployment selects host staging.

3
Post and poll the transfer

The sender uses nixl create_xfer_req/post_xfer_req and polls status. GPUDirect RDMA is the preferred cross-node path; host staging is a configured tier, not automatically an error fallback.

4
Complete, register, enqueue

A transfer_complete handshake lets the receiver wrap the staged bytes as a repository-registered data_batch, then push only its handle onto the destination stream’s input channel.

5
Preserve progress on failure

Same-CN exchange skips this protocol and hands off a handle in-process. For cross-CN failure, the proposal calls for a nixl retry, then bRPC/CPU fallback, and query failure only if both paths fail; the output batch remains owned across attempts.

LEASE
Spilling GPU bytes is not enough if the scarce object is a staging lease

All-to-all exchange can deadlock even with an acyclic query plan. Forward progress requires lease-aware copy-out, a non-borrowable receive-staging floor, copy-out credit, send-copy credit, and a watchdog for “no progress.” Otherwise A can wait for B’s lease while B waits for memory that only A’s send would free.

N

Why nixl instead of direct UCXX

It matches FE-provided point-to-point routes, supplies the metadata side channel and registered-buffer abstraction, can choose among local/GPU/remote paths, and already uses UCX-class backends. The team avoids rebuilding peer discovery, path selection, and staging coordination directly on UCXX.

OWN

Sink-to-nixl ownership is unresolved

The proposed data_batch::release_or_copy_table()—not present in the pinned tree—would steal the table only when the sink is sole owner; otherwise it deep-copies using reserved send-copy credit. Keeping the repository reference preserves spill eligibility but forces the copy. Dropping it enables a steal but leaves the in-flight transfer non-spillable until transfer_complete.

CONFIG
Scope configuration early, but keep it additive

The generic context needs session/operator settings such as item/byte channel capacity, exchange batch targets, coalescing size/time thresholds, staging-arena size, and copy credits. Defaults must leave the non-distributed path unchanged. Future receive-side resource visibility may guide GPU versus host/disk placement, but it belongs on the generic session API—not in a StarRocks-only context subclass.

PR
Standalone does not mean context-free

Each operator PR must still explain the later caller: the Rust session will feed/drain it, FFI will expose lifecycle, the FE plan will determine placement, and the shared resource layer will account for queued data. Isolate code dependencies—not architectural assumptions.

Review order: operator semantics → scheduling/completion → ownership/spill → error/cancel teardown → public API shape → integration. This keeps a wiring failure from hiding a broken core contract.

DEBUG
Locate the broken boundary before opening engine code

No CN in the FE list points to registration/heartbeat. Dispatch failure points to BRPC/Thrift decode. A structured unsupported-node error points to translation. A returned stub row means the current executor seam was reached successfully but real GPU execution was not. A multi-fragment stall belongs to future session/exchange completion, not the single-fragment translator.

Review questions

Answer from the pinned snapshot and the labeled target architecture. A correct answer must preserve both the ownership boundary and maturity level.

1. Who decides which CN receives each shuffle partition?

2. The pinned CN starts a real SiriusContext and a query returns a row containing stub. What does that prove?

3. Which source should a leaf fragment that reads parquet use?

4. The translator encounters a StarRocks plan node with no Substrait mapping. What is the safe behavior?

5. In the target design, a downstream CN stops draining. How should Sirius react first?

6. What is the correct first delivery for the streaming source?

7. In the proposed cross-CN path, when may the receiver expose a batch to the streaming source?

8. What is the intended first resource-management shape for exchange queues?

Trace exercise: take a two-fragment distributed GROUP BY and annotate every transition with (a) owner, (b) representation, (c) memory owner, (d) EOS producer, and (e) implemented/target/proposed status. If any arrow has two owners or no completion edge, the design is incomplete.

Takeaway: StarRocks owns the distributed query; the Rust wrapper owns compatibility and exchange; Sirius owns local GPU execution. Substrait and FFI keep those responsibilities connected without collapsing them.
