A named dock exists at a pipeline boundary

Think freight docks: a producer pipeline drops batches at a named dock, and the dock's rules say when another pipeline may unload. The dock is a port; it points at a repository. Adjacent operators inside one task do not use this dock: the task driver passes the returned operator_data directly forward.

Forward inside the task, publish at the sink

gpu_pipeline_task::compute_task() owns an input operator_data and assigns each execute() return to the next call. Only after the final operator does publish_output() invoke the pipeline sink. The default sink publishes each shared_ptr<data_batch> into every downstream repository-backed port.

{
  auto& pipelineable_output = dynamic_cast<const pipelineable_operator_data&>(output_data);

  }

Three unloading rules

The barrier type is pipeline semantics compressed into one enum. Same repository machinery underneath — only the release rule changes.

🚚

PIPELINE — roll-through dock

Pallets release one at a time, the moment they land. This is how a filter chain streams: each batch flows straight to the next operator in the same pipeline.

🌊

PARTIAL — wave release

Goods release in waves while the shipment is still arriving. CONCAT-after-PARTITION consumes partitions incrementally, across a pipeline boundary.

🏛️

FULL — bonded warehouse

Sealed until the entire shipment clears customs. A hash-join's build side stays invisible until its producing pipeline completely finishes.

Access to representations is controlled by RAII: many read-only holders or one mutable holder. idle describes lock state, not object lifetime.

N

read_only
Any number of concurrent readers. Converters queue behind all of them.

⇄
0

idle
Nobody holds it. The only state that can be locked either way — and the only state that can be spilled.

⇄
1

mutable_locked
Exactly one exclusive holder. Required to mutate — or convert to another memory space.

💡
Spillable = idle + in a registered repository

The downgrade executor searches registered repositories first, then the inspectable scheduler queue for batches held by queued tasks. Both discoverability and idle lock state are load-bearing; ownership and residency are separate questions.

⚠️
How you cause an OOM

Park batches in a private, unregistered queue and they are undiscoverable. Hold accessors “for later” and they are not idle. Proposed Module 10 keeps an authoritative repository lookup and sends only {batch_id, size} metadata through a future channel, but that API is not live code.

History: this tri-class lock design replaced a 4-state FSM (cuCascade #117, adopted in Sirius #689) — lock-discipline races stopped being runtime bugs and became compile errors.

Three tickets

Three incidents, all traceable to this module. Pick your diagnosis.

Your new operator buffers output batches in a private std::deque of locked handles while waiting for a slow consumer. Under memory pressure the query OOMs instead of spilling. Why?

A repository contains a shared_ptr<data_batch> and no accessor is active. What can you conclude?

You wire a streaming producer to its consumer with a FULL barrier. What breaks?

Two operators need the same batch concurrently — one is reading it, the other wants to convert it to host memory. What happens?

Code-reading task: trace one shared_ptr<data_batch> from pipelineable_operator_data through an adjacent execute(), the terminal sink(), repository insertion, and downstream port pop. Observable exercise: inspect a plan with one FULL and one PARTIAL edge and label which batches can be consumed before producer completion. ✓
Recap

Task-local operator_data, batch ownership, accessor locks, repository identity, and residency are different layers. Repositories buffer pipeline edges; they do not replace forward operator returns inside a task.
