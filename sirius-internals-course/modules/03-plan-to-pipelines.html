Push versus pull: classify the call path, not the method name

Jaffray's framing asks who controls the next transfer. In a pull iterator, a consumer recursively calls its child for another tuple or batch. In a push pipeline, a producer or pipeline driver hands an available batch to downstream operators.

What the state machine adds

NEED_MORE_INPUT asks the driver for another source chunk.

HAVE_MORE_OUTPUT keeps the same input active while an operator emits more chunks.

BLOCKED yields the task until an asynchronous source or sink can proceed.

FINISHED supports early termination such as a satisfied limit.

★
Canonical wording

DuckDB uses vectorized push-based pipeline execution. Sirius uses a push-oriented, task-based GPU dataflow architecture with buffered repository boundaries and a pull-like readiness scheduler.

The expression boundary: DuckDB objects stop at planning

Supported expressions are translated once while Sirius builds its physical plan. Operator interfaces carry the native sirius::expression PIMPL; execution code unwraps its sirius::ast::node. DuckDB planner expression classes do not leak through the operator surface.

M

MATERIALIZE

Each expression node becomes a cuDF operation and intermediate cudf::column. Easy to inspect; more launches and intermediates.

A

AST_INTERPRET

Build a cudf::ast::tree and evaluate a subtree with cudf::compute_column. This is the default.

J

AST_JIT

Compile the cuDF AST into a fused kernel with cudf::compute_column_jit. JIT means generated GPU code; fusion means multiple AST operations run in one kernel.

Not every node is AST-eligible. CASE, some functions, and unsupported casts become AST breakers. The executor builds a tree of AST subtrees, materializing only at those boundaries. A translator returning nullopt is a local fallback signal; an expression rejected during plan support checking can instead keep the whole query on DuckDB.

Initialization turns an operator tree into runnable pipelines

sirius_engine::initialize_internal() is the missing bridge between physical-plan creation and task execution. It builds a meta-pipeline tree, runs sirius_pipeline_converter, materializes repository wiring, and hands execution-ready pipelines to the query context.

  → sirius_meta_pipeline::build()
  → sirius_pipeline_converter::convert()

  → planner::query / task scheduler
Do not collapse these stages

The plan generator maps DuckDB logical operators and expressions.

Meta-pipeline construction identifies pipeline structure around sources and sinks.

The converter inserts Sirius-specific partition, concat, sample, partition-sort, and merge stages.

Materialization creates runtime repositories and ports only after a context and repository manager exist.

Wiring is described first and materialized second

sirius_pipeline_converter::compute_repository_wiring() emits plain descriptors. Each descriptor identifies a source operator and pipeline, destination pipeline, port name, and barrier. materialize_repository_wiring() then creates a repository, attaches the destination port, registers the sink's downstream target, and establishes dependency relationships.

!
PIPELINE is not an intra-task edge

Adjacent operators inside one GPU task exchange returned operator_data. Barrier metadata exists on repository-backed edges between pipelines.
