Operator Authoring, Observability, Testing & Teardown

A safe change is wired, measurable, memory-aware, testable, and drainable—not merely correct on one happy-path batch.

The operator-authoring contract

1
Load dependency context first

Run /module-context <task> before changing operator, expression, memory, join, sort, or IO code. Then follow the Super Sirius reading order. This is part of the repository contract, not optional preparation.

2
Name and register

Add the enum in sirius_physical_operator_type.hpp, its ToString case, source/header files, and production plus test CMake entries.

3
Choose the pipeline role

An ordinary transform implements execute(). A boundary may need sink(), ports, hints, task input, or finalization. A scan owns split semantics. A compound operator also needs converter rules and wiring.

4
Define task state

Put shared, pipeline-lifetime data in task global state and batch/retry-specific data in local state. Do not hide query state in a singleton or thread-local.

5
Account for memory and retry

Implement a defensible no_history_peak_memory_estimate(). Decide whether OOM can resume at an operator index or whether the task must be atomic.

6
Finalize once

Override on_finalize_operator(), not finalize_operator(); the base wrapper owns the finalized flag and lifecycle checks.

7
Prove and document

Add focused, integration, CPU-comparison, multi-GPU, and race coverage in proportion to the contracts touched; update docs/super-sirius/ and link it here.

The task-creation lock is an authoring rule

If custom task input consumes pipeline state outside the base path, the critical section must cover the state claim and the task constructor. The source comment is the contract:

sirius_pipeline.hpp:177–182 ↗
//! Callers must hold this lock across the operation
//! that consumes pipeline state (port data pop,
//! partition claim, etc.) and the task constructor
//! that calls mark_task_created(), so that
//! update_pipeline_status() cannot observe an
//! empty-port / balanced-counter state while a task
//! is mid-creation.
Required critical section

Acquire the pipeline status lock.

Pop port data or claim a partition.

Construct the task; construction records mark_task_created().

Release only after the counter and consumed state agree.

RACE
The gap looks like completion

If the lock is released after the pop but before construction, another thread can see empty ports and equal created/completed counters. It can finalize the pipeline while the new task is not yet counted.

Three complementary observability views

LOG

Structured logs

Best for decisions and exceptions: query/pipeline/task IDs, operator index, reservation size, requested bytes, OOM peak, downgrade, retry, and teardown ordering.

NVTX

Profiler timeline

Best for CPU/GPU chronology: query, pipeline, task, operator, and sink ranges aligned with CUDA kernels in Nsight Systems.

Q

Quent telemetry

Best for execution state and relationships: plan edges and ports, queues, threads, routing, reservation, downgrade, compute, and finalization states.

EXPERIMENTAL
Quent's schema is not stable

The exporter and analyzer are active development. Use docs/super-sirius/quent-telemetry.md as the current procedure and avoid building permanent tooling around undocumented fields.

Enable, label, run, visualize
# ~/.sirius/sirius.yaml
sirius:
  telemetry:
    enable_quent: true
    output_directory: telemetry_data
    engine_name: siriusDB

CALL sirius_set_query_label('join_debug_01');
SELECT ...;

pixi run quent telemetry_data
Correlation recipe

Use a unique label; sirius_set_query_label is consumed by the next Sirius query.

Find the query and task IDs in logs.

Match the task's operator and reservation states in Quent.

Use the same time window and operator ID in the NVTX/Nsight trace to decide whether it waited, queued, downgraded, or computed.

Trace drill: if Quent shows a task waiting for reservation, logs show a downgrade request, and NVTX shows no operator range yet, the missing time is admission/memory pressure—not a slow kernel. If NVTX contains a long operator range with a dominant kernel, switch to profiling and source-level optimization.

Test the contract you changed

1
Focused Catch2

Run the smallest real tag, for example pixi run build/release/extension/sirius/test/cpp/sirius_unittest "[expression_executor_ast_native]" or "[bounded_thread_pool]".

2
SQLLogic/integration

Exercise the planner, converter, scheduler, and result path—not only the operator method in isolation.

3
DuckDB CPU oracle

For correctness changes, compare rows, values, nulls, order guarantees, and error behavior against CPU execution.

4
Concurrency scope

Add multi-GPU, OOM/retry, repeated-query, or sanitizer coverage when touching ownership, scheduling, finalization, or device affinity.

5
Repository gates

Run pixi run make test, then pixi run pre-commit run -a. Do not substitute an unrelated familiar tag such as [cpu_cache].

Error teardown: stop the producer of dangling work first

sirius_engine::execute() calls drain_after_error() before query teardown. This is not cleanup polish: task-creation requests contain raw sirius_physical_operator* values owned by the engine's query plan.

1
Report the exception

The completion future receives the failure.

→
2
Stop task creator

Keep its request queue interrupted so completion callbacks cannot enqueue consumable raw pointers.

→
3
Drain work

Clear the top-level queue; quiesce GPU executors and their in-flight tasks.

→
4
Discard stale creation requests

Only now can no executor create another request. Drain again to close the restart race.

→
5
Restart for the next query

Query-owned operators and repositories may be destroyed after all readers are quiescent.

UAF
Wrong order

Draining GPU work while the task creator remains live lets an in-flight completion schedule a downstream request. Query teardown then frees its operator, and the creator later dereferences the stale pointer in get_operator_for_next_task().

Authoring checkpoint

Code-reading task: compare the base operator, GPU scan, concat, and hash join. For each, list which of execute, sink, get_next_task_hint, get_next_task_input_data, on_finalize_operator, and no_history_peak_memory_estimate it owns.

Observable exercise: run one labeled query with Quent enabled and capture a matching Nsight Systems trace. Select one task and classify every non-compute interval as waiting for input, queued, reserving, downgrading, blocked, or finalizing.

Failure scenario: reorder “stop task creator” after “drain GPU executors.” Explain the exact callback, queued object, pointer owner, and dereference that form the use-after-free window.

A custom boundary operator pops a port batch, releases the status lock, and then constructs its task. What can happen?

Why must drain_after_error() stop the task creator before draining GPU executors?

✓
Recap

Choose an operator shape from its pipeline role, preserve task accounting and reservation contracts, instrument the state transitions that matter, select tests by the changed contract, and treat teardown ordering as part of correctness.
