Design Decisions & Tradeoffs

Why you should care

These two currents explain almost every decision below — and new code that swims against them gets rewritten. Knowing them is the difference between a PR that merges and a PR that gets a history lesson.

Eight decisions, eight receipts

Each card is one standing decision: what was decided, why it stuck, and the PR where it happened. Contradict one in review and someone will paste you the receipt.

🧩

Extension, not engine

Riding inside DuckDB bought a parser, optimizer, and catalog for free on day one. The coupling was the price — Current 1 is that debt being repaid deliberately.

2024 inception · #643 · #880 · #908

⚒️

cuDF over hand-written kernels

Every operator got cheaper to build and faster to trust, with cuco hash tables inherited for free. The legacy kernels were deleted wholesale in Jun 2025.

#6

🏗️

Total rewrite: Super Sirius

The old gpu_executor was single-threaded — no overlap, no memory tiering, no way to retrofit either. The task-based pipeline engine was built alongside it, then cut over.

#96 · #198 · #206

📦

Repositories at pipeline boundaries

Inside one task, operators return operator_data forward. A terminal sink publishes data_batch references into repositories at pipeline boundaries, buying buffered scheduling, barriers, discoverability, and downgrade without imposing a repository between every operator call (Module 6).

cc#26 · #519 · #689

📐

Descriptors now, wiring later

Plan-time code emits repository wiring descriptors through a pipeline_build_context; materialization happens once an engine exists. Planning stays engine-free and testable.

#607 · #770

🕶️

Transparent interception

GPU support is a plan-generator decision made inside an optimizer extension — invisible to users, with CPU fallback as the safe default. No special syntax, ever.

#518 · #673

🧯

Downgrade is an executor

Spilling is scheduled work with its own threads and priorities — not an allocator callback firing at the worst possible moment, inside someone else's stack frame.

#97 · #368 · #579 · #647

🧲

Locality first, reservation-device authority

Work follows data across GPUs, and the device that reserved the memory has the final word. The #732→#827 backpressure regression is why the authority rule exists.

Six current ADRs

Each record states the current design as-is. “Revisit” is a testable condition, not a prediction.

FLOW

Push-oriented hybrid execution

Context: GPU tasks need forward batch execution, but pipelines must be independently admitted and memory-managed.
Decision: drive operator_data forward inside a task; buffer pipeline edges in repositories; discover readiness with hints.
Benefit: batching, asynchronous scheduling, barriers, and downgrade.
Cost: explicit completion/re-arm protocol and harder liveness reasoning.
Status/evidence: Current—gpu_pipeline_task, task_creator, operator sink/ports.
Revisit if: a unified driver can preserve those properties with measurably simpler lifecycle semantics.

AST

Translate once into sirius::ast

Context: DuckDB expression classes couple operator execution to one frontend.
Decision: translate at planning into native expression/value/function types; lower to cuDF AST or materialized operations later.
Benefit: a stable engine boundary and non-DuckDB frontend path.
Cost: Sirius owns translation, type coverage, AST breakers, and fallback tests.
Status/evidence: Current—src/expression/ and src/expression_executor/.
Revisit if: a frontend-neutral shared IR satisfies the same ownership and GPU-lowering requirements.

SPLIT

Expand compound operators into pipelines

Context: join, aggregate, and global sort need partition/build/merge phases with different barriers.
Decision: let sirius_pipeline_converter insert PARTITION/CONCAT and sample/partition/merge chains.
Benefit: explicit scheduling, device affinity, and phase-specific memory state.
Cost: more pipelines, wiring, IDs, and completion edges.
Status/evidence: Current—converter split helpers and plan printer.
Revisit if: an operator can expose equivalent phases without hiding scheduler-visible state.

WIRE

Describe wiring before materializing it

Context: pipeline conversion should not require live repositories or a runtime manager.
Decision: emit repository_wiring data, then materialize repositories, ports, consumers, and dependencies in initialize_internal().
Benefit: deterministic, testable planning and explicit runtime ownership.
Cost: two representations that must remain consistent.
Status/evidence: Current—compute_repository_wiring() and repository_wiring_materializer.cpp.
Revisit if: planning gains a runtime-independent repository abstraction with equal testability.

LOCK

Atomic state claim and task accounting

Context: completion can race a port pop or partition claim before the new task is counted.
Decision: hold the pipeline status lock across state consumption and the constructor that calls mark_task_created(); use RAII completion accounting.
Benefit: no empty-port/balanced-counter false finish.
Cost: a wider critical section and strict custom-task discipline.
Status/evidence: Current—load-bearing comment in sirius_pipeline.hpp.
Revisit if: state claims and task counts become one atomic reservation primitive.

TRACE

Observability is execution state

Context: latency can be input wait, queueing, reservation, downgrade, GPU compute, or finalization; one timer cannot disambiguate them.
Decision: carry IDs and states through structured logs, NVTX ranges, and experimental Quent telemetry.
Benefit: cross-layer correlation and actionable performance/debug evidence.
Cost: instrumentation overhead, schema evolution, and ID discipline.
Status/evidence: Logs/NVTX current; Quent experimental.
Revisit if: one stable trace schema covers all three consumers without losing profiler integration.

Archaeology: reading a bug's fossil

Decisions also fossilize at line granularity. Pipelines were once declared finished while tasks were still in flight — the query-end SEGFAULT saga (#766, #788, #804) — so mark_task_completed now audits its own invariant on entry.

src/pipeline/sirius_pipeline.cpp · L427-436 ↗ reader mode

{
Sanity check: a task is completing here, which means this pipeline was still running work. If the pipeline was already marked finished, or any of its operators were already finalized, then we declared the pipeline done too early — i.e. a task was still in flight when we considered the pipeline complete. That mismatch can make the whole query look done while work is still running, so surface it loudly.
  const bool pipeline_was_finished = pipeline_finished.load();
  std::string finalized_ops;
Plain English

A task is reporting completion. Sounds routine — this exact moment used to SEGFAULT whole queries.

Six lines of comment guarding two lines of code: that ratio is the scar, not the wound.

The invariant, stated plainly: if a task is finishing here, nobody may have already declared this pipeline done.

And the failure mode it fossilizes: the query looks complete, teardown begins, and live tasks are still touching freed state.

Evidence sample one: atomically read whether someone already flipped the finished flag.

Evidence sample two: start collecting the names of any already-finalized operators — for the loud log this is about to write.

Why the comment is load-bearing

Without it, this check reads as paranoia and some future cleanup PR deletes it. The comment stores which incident produced the code — the ring around the scar — so the invariant survives its authors.

Three review comments

Three PRs, three reviewer questions. Answer as the author — with receipts.

You're adding an operator that must hand result batches to an external process. Which two standing decisions dictate where those batches live and how they're referenced?

You want to teach the planner a new DuckDB expression type. Which direction does the codebase want you to go?

A reviewer asks why your pipeline-construction change takes a pipeline_build_context instead of sirius_engine&. What's the answer?

Code-reading task: choose one ADR and verify every “Current” claim against source rather than its PR. Observable exercise: take a proposed change and write context, decision, benefit, cost, evidence, status, and a measurable revisit condition. Failure scenario: use historical PR text as proof of current behavior and identify the source/test that disproves it.

Recap

Architecture is a set of active tradeoffs. Current source establishes behavior; history supplies provenance; an ADR remains useful only when its cost and reconsideration condition are visible.
